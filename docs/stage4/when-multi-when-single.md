# 何时用多 Agent：单 Agent vs 多 Agent 的决策

> 阶段 4 概念文档 | 配合 Task 4.1、4.2、4.3 阅读

---

## 1. 本质是什么

这篇是 `division-of-labor.md` 的决策篇。理解了多 Agent 的本质后，真正难的不是"怎么做多 Agent"，而是**"什么时候该用多 Agent，什么时候单 Agent 就够"**。

这是系统设计判断题。**90% 的新手错误是"过度使用多 Agent"**——把本该单 Agent 解决的问题拆成多个，结果更慢、更贵、更难调。

## 2. 决策的核心原则

一句话原则：

> **先用单 Agent，直到你遇到单 Agent 解决不了的具体瓶颈，才考虑多 Agent。**

这不是保守，是工程纪律。多 Agent 引入复杂度，必须有充分理由。

### 为什么"默认单 Agent"

Anthropic（Claude 的公司，Agent 领域权威）的经验数据：

```
他们观察大量生产 Agent 后发现：
  - 多数成功案例是单 Agent + 好工具
  - 过早拆成多 Agent 的项目，大多以"难维护"告终
  - 单 Agent 的瓶颈，往往通过"加工具/改 prompt"就能解决，不需要拆
```

**先穷尽单 Agent 的优化，再考虑拆分。**

## 3. 决策框架：什么时候真的需要多 Agent

给你一个判断清单。**只有出现以下情况，才考虑多 Agent：**

### 信号 1：上下文窗口真的不够（最硬的理由）

```
场景：要让 Agent 处理一个超大任务，单 Agent 的上下文被撑爆
  - 调研需要读 100 篇文档，全塞进一个 Agent 上下文爆了
  - 解决：拆成多个调研 Agent，各自读一部分，最后汇总
```

**这是唯一"技术上必须"拆的理由。** 其他理由都是"可以拆但不必须"。

### 信号 2：角色指令严重冲突

```
场景：同一个 Agent 既要"严谨求证"又要"天马行空创作"
  - 两种人设塞给一个 Agent，它精神分裂，两边都做不好
  - 解决：拆成"验证 Agent"和"创作 Agent"
```

### 信号 3：需要并行加速

```
场景：3 个独立子任务可以同时做，串行太慢
  - 同时调研 3 个不同技术方向
  - 解决：3 个 Agent 并行，速度提升近 3 倍
```

### 信号 4：需要交叉验证

```
场景：结果很重要，不能信任单一 Agent 的输出
  - 生成安全审计报告，需要多个 Agent 独立审查交叉确认
  - 解决：多 Agent 独立产出 + 裁决 Agent
```

**如果以上信号都没有，用单 Agent。** 别为了"显得高级"而拆。

## 4. 反信号：这些情况千万别用多 Agent

### 反信号 1：任务有明确固定顺序

```
✗ 错误：把"A→B→C 固定流水线"拆成 3 个 Agent
✓ 正确：用单 Agent + LangGraph 状态图（Task 2.4 那种）
```

固定流程用状态机，不是多 Agent。多 Agent 是为"动态分工"，固定流程不需要动态性。

### 反信号 2：任务很简单

```
✗ 错误：查个天气、回答个简单问题，搞 3 个 Agent
✓ 正确：单 Agent 一次搞定
```

简单任务用多 Agent 是杀鸡用牛刀，还增加故障点。

### 反信号 3：你想"看起来更 AI"

```
✗ 错误：觉得多 Agent 更酷、更先进，所以用
✓ 正确：以解决问题为准，不为多 Agent 而多 Agent
```

这是最常见的心理误区。**技术选型看效果，不看炫酷度。**

## 5. 拆分粒度：拆几个 Agent

如果你确定要用多 Agent，**拆几个**？经验法则：

```
2-3 个：最常用，性价比最高
  典型：调研 + 写作；规划 + 执行

4-5 个：复杂任务，有明确分工
  典型：调研 + 分析 + 写作 + 审校

>5 个：很少值得，通常是过度设计
  除非是大型的、角色天然多样的任务（如模拟一个团队）
```

**粒度原则：每个 Agent 应该有清晰的单一职责。** 如果两个 Agent 职责重叠，合并它们；如果一个 Agent 干两件不相关的事，才考虑拆。

## 6. 成本意识：多 Agent 的真实代价

这是决策时最容易忽视的。多 Agent 不是免费的：

```
单 Agent 处理一个任务：
  LLM 调用次数：N 次（循环 N 轮）
  成本：C

3 个 Agent 串行处理同一任务：
  LLM 调用次数：约 3N 次（每个 Agent 各自循环）
  成本：约 3C
  延迟：约 3 倍

3 个 Agent 并行：
  成本：约 3C
  延迟：约 1 倍（并行省时间，但不省钱）
```

**关键认知：**
- 多 Agent 几乎一定**更贵**（更多 LLM 调用）
- 并行能省**时间**，但省不了**钱**
- 通信开销（Agent 间传递上下文）也是 token 成本

**所以多 Agent 必须换来相应的价值（专注/并行/验证），否则就是浪费。**

## 7. 嵌入式类比：要不要上 RTOS

这个类比会帮你做决策：

| 多 Agent 决策 | 嵌入式决策 |
|--------------|-----------|
| 单 Agent 够不够？ | 裸机循环够不够？ |
| 任务复杂到要分工？ | 系统复杂到要上 RTOS？ |
| 2-3 个 Agent | 几个任务 |
| 通信开销 vs 分工收益 | RTOS 开销 vs 多任务收益 |

**你肯定遇到过：** 一个简单的 MCU 项目，别人非要上 FreeRTOS，结果调度开销比业务逻辑还大，调试还复杂。你会想"裸机 while 循环就够了"。

**多 Agent 完全一样。** 简单需求上多 Agent，就像简单项目硬上 RTOS——增加复杂度但没换来价值。

**成熟的嵌入式工程师知道：while 循环能解决的就别上 RTOS。成熟的 Agent 开发者知道：单 Agent 能解决的就别拆多 Agent。**

## 9. 常见误解纠正

### 误解 1："多 Agent 是 Agent 开发的进阶，所以要学就要用"

**错。** 学多 Agent 是为了**知道什么时候用、什么时候不用**，不是为了到处用。学会"克制地用多 Agent"才是真本事。

### 误解 2："单 Agent 是初级的，多 Agent 是高级的"

**错。** 单/多 Agent 没有高低之分，是不同场景的工具。用单 Agent 解决复杂问题是高手，硬拆多 Agent 反而是菜鸟。

### 误解 3："用多 Agent 才像真正的 Agent 系统"

**错。** Anthropic、OpenAI 的多数生产案例都是单 Agent。"是不是 Agent"看的是有没有循环+工具+自主决策，不是看 Agent 数量。

## 10. 一句话本质

> **多 Agent 是工具，不是目标。决策原则：先用单 Agent，遇到具体瓶颈（上下文爆/指令冲突/需并行/需验证）才拆，且拆 2-3 个为宜。多 Agent 几乎一定更贵更复杂，必须换来相应价值。成熟的开发者会克制地用多 Agent——就像成熟的嵌入式工程师会克制地用 RTOS。**
