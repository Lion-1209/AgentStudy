# 多 Agent 的本质：分工协作

> 阶段 4 概念文档 | 配合 Task 4.1、4.2 阅读

## 1. 本质是什么

多 Agent（Multi-Agent）听起来很高深，但剥开看，它的本质极其朴素：

**多 Agent = 把一个大任务，拆给几个专职 Agent 各干一段。**

就像公司里不是一个人干所有事，而是有人调研、有人分析、有人写报告。多 Agent 就是把这种"分工"搬到 LLM 上。

更本质地说：

> **多 Agent 的本质是"一个 Agent 的输出，变成另一个 Agent 的输入"。**

去掉所有框架的黑话，就这一句话。Task 4.2 你会手写一遍来验证这一点。

## 2. 为什么需要多 Agent（单 Agent 不够吗）

这是最关键的问题。**很多人过度使用多 Agent，其实单 Agent 就够。** 先理解"为什么需要"，再决定"用不用"。

### 单 Agent 的瓶颈

一个 Agent 干所有事时，会遇到这些问题：

```
问题1：上下文污染
  一个 Agent 既要调研又要写报告，调研的细节会占满上下文，
  写报告时它"忘了"调研重点，或者被无关信息干扰

问题2：指令冲突
  "你是严谨的调研员" 和 "你是文笔流畅的作家" 
  塞给同一个 Agent，它人格分裂，两边都做不好

问题3：无法并行
  调研 A 和调研 B 本可以同时做，单 Agent 只能串行，慢

问题4：错误放大
  一个 Agent 在早期步骤犯错，后面全跟着错，没有"独立校验"
```

### 多 Agent 怎么解决

```
分工解决上下文污染：
  调研 Agent 只管调研（上下文干净）
  写作 Agent 只管写作（上下文干净）

专职解决指令冲突：
  调研 Agent = 严谨人设
  写作 Agent = 文笔人设
  各自专注，互不干扰

并行解决速度问题：
  3 个调研 Agent 同时查 3 个方向

独立校验解决错误放大：
  审校 Agent 独立检查写作 Agent 的输出
```

**多 Agent 的价值 = 分工带来的专注 + 并行 + 交叉验证。**

## 3. 心智模型：多 Agent = 一个团队

| 多 Agent 概念 | 团队类比 |
|--------------|---------|
| 单个 Agent | 一个员工（有岗位职责） |
| Agent 间通信 | 同事交接工作 |
| Pipeline（管道） | 流水线（A 干完交给 B） |
| Supervisor（主管） | 项目经理（分配任务） |
| Debate（辩论） | 评审会（互相挑刺） |

**最关键的洞察：** 你管理过团队或参与过项目吧？你知道"分工"不是越多越好——人多了沟通成本暴涨，反而效率低。多 Agent 完全一样。**2-3 个专职 Agent 往往比 10 个 Agent 更有效。**

## 4. 三种核心协作模式

这是多 Agent 的"设计模式"。理解这三种，你能组合出任何协作方式。

### 模式 1：Pipeline（管道/流水线）

```
调研 Agent → 分析 Agent → 写作 Agent
   张三        李四         王五
```

**本质：** 串行，前一个的输出是后一个的输入。像工厂流水线。

**适用：** 有明确顺序的任务（调研→分析→报告）。

**类比：** Unix 管道 `cat | grep | sort`。

### 模式 2：Supervisor（主管/调度）

```
            ┌→ 代码 Agent
Supervisor ─┼→ 架构 Agent
            └→ 安全 Agent
```

**本质：** 一个主管 Agent 接收任务，判断该派给谁，分发后再汇总。

**适用：** 任务需要动态分配（根据问题类型找不同专家）。

**类比：** 医院分诊台——你不知道挂什么科，分诊护士帮你分配。

### 模式 3：Debate（辩论/对抗）

```
Agent A（正方）↔ Agent B（反方）
       ↓
   评审 Agent（裁决）
```

**本质：** 多个 Agent 针对同一问题给出不同观点，互相质疑，最后裁决。

**适用：** 需要高质量决策、避免单一视角偏见（如方案评审）。

**类比：** 论文同行评审——多个审稿人挑刺，提高质量。

## 5. 通信机制的本质：消息传递

Agent 之间怎么"说话"？**就是字符串传递。**

```python
# Task 4.2 你会手写的：
output_a = agent_a.run("调研 LangGraph")
#       ↑ Agent A 的输出是一段文本

output_b = agent_b.run(output_a)
#                    ↑ 把 A 的文本喂给 B 当输入
```

**没有魔法。** 所谓"Agent 通信"，就是把一个 Agent 输出的文本，作为另一个 Agent 的输入。和函数调用传参一模一样。

### 为什么这很重要

理解了"通信 = 文本传递"，你就明白：

```
框架（CrewAI、AutoGen）做的事：
  ✓ 把"文本传递"包装得更优雅（context 参数、消息路由）
  ✓ 加上日志、追踪
  ✓ 提供角色定义模板

框架没做的事（你手写也能做）：
  ✗ 没有什么"Agent 真的在交流"
  ✗ 底层就是字符串传来传去
```

**Task 4.2 的价值：** 手写一遍多 Agent，你会发现"去掉框架后，多 Agent 就是几个函数互相传字符串"。神话感消失，你获得掌控感。

## 6. 嵌入式类比：多任务系统

| 多 Agent | 嵌入式多任务 |
|---------|------------|
| 多个 Agent | 多个任务（task/thread） |
| Agent 间通信 | 任务间通信（消息队列、共享内存） |
| Supervisor 调度 | RTOS 调度器 |
| Pipeline | 任务链 |
| 并行 Agent | 并发任务 |

**关键差异（必须注意）：**

嵌入式多任务是为**速度**（CPU 分时复用）。多 Agent 并行也是为速度，但更多是为**专注和分工**（不同 Agent 用不同 prompt/工具）。

**别混淆的点：** 多 Agent 不是为了"并发编程"，而是为了"角色分工"。即使串行跑，分工的价值依然存在（专注、上下文隔离）。

## 7. 常见误解纠正

### 误解 1："Agent 越多越厉害"

**大错。** 这是新手最常犯的错。Agent 多了：
- 通信成本暴涨（每个 Agent 都要 LLM 调用，贵且慢）
- 错误传播路径变长（一个错，连锁影响）
- 调试噩梦（不知道哪个 Agent 出了问题）

**业界共识：能用 1 个 Agent 解决的，别用 2 个；能用 2 个的，别用 5 个。** Anthropic 明确建议：先尝试单 Agent，遇到瓶颈再加。

### 误解 2："多 Agent = 真 AI 协作"

**错。** Agent 之间没有真正的"理解"或"协商"。它们只是在传递文本。所谓"协作"，是你设计的通信流程产生的效果。**多 Agent 是一种系统设计，不是 AI 觉醒。**

### 误解 3："用框架才能做多 Agent"

**错。** Task 4.2 会证明，纯 Python 几十行就能做多 Agent。框架（CrewAI）只是让你写得更快、更规范。**理解原理后用框架才有意义，否则只是套模板。**

### 误解 4："Pipeline 和 Supervisor 是不同的技术"

**本质上是同一技术的不同组织方式。** 底层都是"Agent 输出 → 另一个 Agent 输入"。Pipeline 是固定路由，Supervisor 是动态路由。理解了通信本质，模式只是路由策略。

## 8. 一句话本质

> **多 Agent = 把大任务拆给几个专职 Agent，本质是"一个 Agent 的输出变成另一个的输入"。它的价值是分工（专注 + 并行 + 交叉验证），代价是通信成本和复杂度。能用单 Agent 别用多 Agent，用了也尽量少（2-3 个为宜）。**
