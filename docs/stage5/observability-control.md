# 可观测性：黑盒系统的控制论

> 阶段 5 概念文档 | 配合 Task 5.2 阅读

---

## 1. 本质是什么

可观测性（Observability）的本质是：**让你能"看见"系统内部发生了什么。**

这不是可选的工程装饰，而是 Agent 开发的**生存必需**。因为 Agent 和传统软件有根本区别：**传统软件是确定性的，Agent 是概率性的黑盒。**

没有可观测性，Agent 出问题时你两眼一抹黑——它为什么调了那个工具？为什么走了那条路？为什么输出这个结果？你完全不知道。**调试黑盒是不可能的。**

## 2. 为什么 Agent 比传统软件更需要可观测性

### 传统软件：确定性 + 局部状态

```
传统程序出 bug：
  - 报错堆栈告诉你哪一行错了
  - 状态可预测（同样输入同样输出）
  - 加 print/断点就能定位
```

传统软件是"白盒"——逻辑是你写的，状态可追踪，确定性让你能复现问题。

### Agent：概率性 + 分布式状态 + 长链路

```
Agent 出问题：
  - 没有"报错"，它只是输出了不该输出的东西
  - 同样输入，不同次运行可能不同（LLM 是概率的）
  - 状态分散在多轮对话、多个工具调用里
  - 决策链可能几十步，出问题的点可能在第 5 步
```

Agent 是"黑盒"——决策由 LLM 做（你看不到它"怎么想的"），状态分散，行为不确定。

**黑盒系统的调试，必须靠"观测"。** 这就是为什么可观测性对 Agent 是刚需，对传统软件是锦上添花。

## 3. 心智模型：控制论视角

你做嵌入式一定懂这个：**要控制一个系统，先得能观测它。**

| Agent 可观测性 | 嵌入式调试 |
|---------------|-----------|
| Tracing（追踪） | 逻辑分析仪 / 示波器 |
| 看每步输入输出 | 看每个信号的波形 |
| Token / 延迟监控 | 时序 / 功耗分析 |
| 评估（evaluation） | 单元测试 / 验收测试 |
| LangSmith / Langfuse | JTAG 调试器 / 串口 log |

**核心相似点：** 你调嵌入式时，示波器和逻辑分析仪是"眼睛"——没有它们，你只能盲猜。Agent 一样，trace 工具就是你的"逻辑分析仪"。

**没逻辑分析仪调硬件 = 瞎猜。没 trace 工具调 Agent = 瞎猜。**

## 4. 可观测性的三个层次

### 层次 1：Tracing（追踪）— 看过程

**看 Agent 每一步做了什么。**

```
一次 Agent 运行的 trace：
  第1步：LLM 决策 → 调用工具 search("天气")
  第2步：工具返回 → "北京 晴天 25°C"
  第3步：LLM 决策 → 调用工具 calculate("...")
  第4步：工具返回 → "8"
  第5步：LLM 输出最终答案
```

**解决的问题：** "Agent 为什么这么做？""它在哪一步偏离了预期？"

**工具：** LangSmith、Langfuse（你 Task 5.2 会用）。

### 层次 2：Metrics（指标）— 看效率

**量化 Agent 运行的成本和性能。**

```
关键指标：
  - 总 token 用量（输入+输出）→ 成本
  - 总延迟 → 用户体验
  - 循环次数 → 效率
  - 工具调用成功率 → 稳定性
  - 每步的 token/延迟 → 找瓶颈
```

**解决的问题：** "为什么这么贵？""为什么这么慢？""哪个工具拖后腿？"

### 层次 3：Evaluation（评估）— 看质量

**系统性判断 Agent 输出好不好。**

```
评估方法：
  - 准备测试集（一批标准问答）
  - 跑 Agent，收集输出
  - 用规则/LLM/人工打分
  - 跟踪分数变化（改了 prompt，变好还是变坏？）
```

**解决的问题：** "我这个 Agent 到底行不行？""改了之后是进步还是退步？"

**这是最被忽视的层次。** 没有评估，你永远不知道 Agent "好不好"，只能凭感觉猜。

## 5. Tracing 的本质：把黑盒变白盒

这是可观测性的核心。讲透它的价值：

### 没有 Trace 时

```
result = agent.run("帮我分析这个项目")
# 输出："项目分析完成，建议..."

问题：这个结论怎么来的？可信吗？我不知道。
     如果错了，错在哪？我不知道。
```

Agent 是黑盒，输出像凭空出现。

### 有 Trace 时

```
result = agent.run("帮我分析这个项目")
# trace 显示：
#   - 读了 5 个文件（哪些？）
#   - 调了 3 次工具（成功几次？）
#   - LLM 推理了 4 轮（每轮想了什么？）
#   - 总共花了 5000 token、12 秒

现在你能看到：它读了哪些文件、怎么推理的、在哪卡住。
黑盒变白盒。
```

**Trace 把"一次 Agent 运行"分解成"可审计的步骤序列"。** 出问题时你能精确指到第几步。

## 6. 为什么从阶段1 就该建立可观测性意识

可观测性不该等到阶段5。回顾你的阶段1 代码：

```python
for i in range(max_iterations):
    print(f"--- 迭代 {i + 1} ---")          # ← 这就是最原始的 trace
    print(f"LLM 输出:\n{assistant_message}")  # ← 打印每步
    print(f"工具结果: {tool_result}")         # ← 打印工具结果
```

**你已经在做最基础的 tracing 了！** 那些 `print` 就是 trace。阶段5 的 LangSmith 只是把 print 升级成专业可视化工具。

**养成习惯：写 Agent 永远先加 trace。** 没有观测的 Agent，调试时你会痛不欲生。

## 7. 评估（Evaluation）的本质：Agent 的单元测试

这是最该向你这个工程背景的人强调的。你写代码会写单元测试吧？**Agent 也需要"测试"，就是 evaluation。**

### 传统单元测试 vs Agent 评估

```
传统单元测试：
  assert add(1, 2) == 3          ← 确定性，能精确断言

Agent 评估：
  Agent 回答"北京天气" → 怎么断言？
    - 不能 assert 输出 == 某个固定值（LLM 输出每次不同）
    - 只能评估："是否提到了天气？""是否提到了北京？""是否有事实错误？"
```

**Agent 评估的本质：从"精确相等断言"退化成"质量打分"。** 因为输出不确定，只能打分不能精确比较。

### 三种评估方法

```
1. 规则评估（最简单）
   "输出是否包含'北京'？""是否是 JSON 格式？"
   优点：快；缺点：只能查表面

2. LLM 评估（最常用）
   让另一个 LLM 当裁判，给输出打分
   "这个回答准确吗？1-5 分"
   优点：灵活；缺点：裁判 LLM 也有偏差

3. 人工评估（最准）
   人来看，打分
   优点：准；缺点：慢、贵
```

**实践：** 用规则 + LLM 评估做日常迭代，用人工评估做关键验收。

## 8. 常见误解纠正

### 误解 1："我的 Agent 能跑就行，可观测性以后再说"

**大错。** 等出问题再补 trace，你会发现自己根本不知道出过什么问题（没记录）。**可观测性是基础设施，必须从第一行代码就有。** 就像你不会等系统崩了才加日志。

### 误解 2："print 够用了，不用专业工具"

**部分错。** print 适合简单 Agent。但 Agent 一旦复杂（多步、多工具、多 Agent），print 的输出会变成无法阅读的洪水。**专业工具（LangSmith）的价值在结构化、可视化、可查询。** 简单场景 print 够，复杂场景必须上工具。

### 误解 3："评估太麻烦，我手动看看输出就行"

**错。** 手动看输出只能发现"明显错误"，发现不了"系统性退步"。比如你改了 prompt，80% 场景变好了，20% 变差了——手动看几个例子你只会看到变好的，以为进步了。**没有系统评估，你对自己的 Agent 质量是盲目的。**

### 误解 4："可观测性是为了找 bug"

**部分对。** 找 bug 是主要用途，但不止于此。可观测性还用于：
- 成本优化（找到烧 token 的地方）
- 性能优化（找到慢的步骤）
- 质量评估（量化改进效果）
- 用户分析（看用户怎么用 Agent）

## 9. 一句话本质

> **Agent 是概率性黑盒，调试它必须靠观测。可观测性把黑盒变白盒，三个层次：Tracing（看过程）、Metrics（看效率）、Evaluation（看质量）。从第一行代码就该建立——没有观测的 Agent 调试时是瞎子摸象。对工程背景的你，这就是 Agent 的"逻辑分析仪 + 单元测试"。**

## 10. 你将经历的代码，对应到这里

```python
# 阶段1（原始 trace）：用 print
print(f"迭代 {i}: {result}")

# 阶段2+5（专业 trace）：用 LangSmith
import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "..."
# 之后所有 LangChain 调用自动被追踪
# 在 LangSmith 网页看到可视化 trace
```

**从 print 到 LangSmith，就是从"串口 log"到"逻辑分析仪"的升级。**
