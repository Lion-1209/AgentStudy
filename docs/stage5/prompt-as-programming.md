# Prompt 即编程：给 LLM 写的"程序"

> 阶段 5 概念文档 | 配合 Task 5.1 阅读

---

## 1. 本质是什么

Prompt 不是"和 AI 聊天的话术"。**Prompt 本质上是你写给 LLM 的一段程序。**

这是最该建立的认知转变。一旦你把 prompt 当"程序"而不是"聊天"，你的 prompt 工程思维就对了：

```
误解：prompt 是聊天，写得好不好凭感觉
正解：prompt 是程序，写得好不好看输出是否稳定可控
```

LLM 的行为**几乎完全由输入（prompt）决定**。同样的模型，prompt 不同，行为天差地别。所以"调 prompt"本质上就是"编程"——只不过你用的不是 Python 语法，而是自然语言。

## 2. 为什么 Prompt 是 Agent 的最大变量

回顾 Agent 四要素（阶段1 学的）：LLM + Tool + Loop + Memory。

**其中三个都依赖 prompt 质量：**

```
LLM 决策质量    ← 取决于 system prompt 写得好不好
工具选择准确性  ← 取决于工具 description 写得好不好
记忆利用效率    ← 取决于怎么把记忆注入 prompt
```

工具可以买、循环可以抄、记忆可以用现成方案。**唯独 prompt，必须你自己写，且直接决定效果上限。**

这就是为什么 Prompt Engineering 排在阶段5 第一个——它影响后面所有内容（RAG 质量、Agent 行为、多 Agent 协作）。

## 3. 心智模型：Prompt 是声明式程序

| 概念 | 类比 |
|------|------|
| Prompt | 程序源代码 |
| LLM | 解释器/执行引擎 |
| 调 prompt | 调试程序 |
| Few-shot（给示例） | 单元测试用例 |
| 输出格式约束 | 类型系统/接口定义 |

**最关键的洞察：** Prompt 是**声明式**编程——你描述"要什么结果"，而不是"怎么一步步做"。这和你写命令式代码（for/if）不同。

```
命令式（Python）：          声明式（Prompt）：
for item in list:           "把列表里的偶数挑出来"
    if item % 2 == 0:
        print(item)
```

声明式的代价：**你无法精确控制执行过程，只能通过描述影响输出。** 这就是为什么 prompt 工程是"模糊的艺术"——你在引导一个概率模型，不是执行确定性代码。

## 4. 核心 Prompt 技巧的本质

各种 prompt 技巧看起来花哨，本质都是在解决"如何更可靠地引导 LLM"。逐个看透：

### Few-shot（给示例）= 提供参考实现

```
"翻译成英文：
 苹果 → apple
 香蕉 → banana
 橘子 → ?"
```

**本质：** 你给 LLM 看几个"输入→输出"的样例，让它模仿。就像给函数传几个测试用例，让它推断出模式。**这是最可靠的引导方式——示例比描述更精确。**

### Chain of Thought（思维链）= 让它展示推理

```
"请一步步思考后回答"  vs  "直接回答"
```

**本质：** LLM 是逐 token 生成的。让它"先写推理过程再写答案"，等于给它更多 token 来"思考"，答案质量更高。**类比：** 让人"想好再说"比"脱口而出"质量高。

### 结构化输出约束 = 定义接口契约

```
"请严格按 JSON 格式输出：{"name": ..., "age": ...}"
```

**本质：** 给输出定"类型"，减少自由度。和 Function Calling（阶段1）是同一思想——用结构化契约降低不确定性。

### Role/Persona（角色扮演）= 注入领域知识倾向

```
"你是一位有 20 年经验的资深安全审计专家"
```

**本质：** 激活 LLM 训练数据里"专家"相关的模式，让它输出更专业。**注意：** 这不是真的"变成专家"，只是概率上倾向专业表述。

## 5. Prompt 的核心难题：模糊性

这是 prompt 工程的根本难点。看个例子：

```
你的 prompt："写一个简洁的总结"

问题：
  - "简洁"是多简洁？100字？50字？3句话？
  - "总结"总结哪些要点？
  - 语气正式还是随意？

LLM 会按它自己的理解来，每次可能不同。
```

**Prompt 工程的本质，就是消除模糊性。** 所有技巧最终都指向这个目标：

```
模糊 → 精确的策略：
  "简洁"        → "不超过 100 字"
  "写得好"      → 给 3 个 few-shot 示例
  "按要求格式"  → 给严格 JSON schema
  "专业一点"    → 明确角色 + 领域
```

**好 prompt 的标准：足够精确，让 LLM 的输出可预期、可复现。**

## 6. 嵌入式类比：Prompt 像配置寄存器

| Prompt 工程 | 嵌入式 |
|------------|--------|
| 模糊的描述 → 不稳定行为 | 寄存器位没配好 → 外设行为异常 |
| 加约束 → 行为可控 | 严格按 datasheet 配位 → 行为确定 |
| few-shot 示例 | 参考厂商给的初始化代码 |
| 调 prompt 迭代 | 调寄存器值调试 |
| 不同 LLM 对同一 prompt 反应不同 | 不同芯片寄存器定义不同 |

**核心相似点：** datasheet 写得越细，你配寄存器越不会错；prompt 写得越精确，LLM 输出越可控。**两者都是在消除"模糊地带"。**

## 7. Prompt 的迭代方法论

Prompt 不是一次写对的。它像调试代码，要迭代。给你一个方法论：

```
1. 写初版 prompt
2. 用几个测试输入跑一遍
3. 看哪里输出不符预期
4. 分析原因：是太模糊？缺示例？格式没约束？
5. 针对性修改
6. 重复 2-5，直到稳定
```

**关键：要建立测试集。** 准备 5-10 个代表性输入，每次改 prompt 都用这同一批测试，才能客观比较"改好了还是改坏了"。

**没有测试集的 prompt 调优 = 瞎调。** 你改一版觉得"好像好了"，换个输入又崩了。这和不做单元测试就改代码一个道理。

## 8. 常见误解纠正

### 误解 1："Prompt 工程是玄学，凭感觉"

**错。** 好的 prompt 工程是工程，不是玄学。它有方法论（测试集、迭代、约束）。凭感觉调 prompt 的人，是因为没建立系统方法。**把 prompt 当代码，用工程方法调，就是科学。**

### 误解 2："Prompt 越长越好"

**错。** 长 prompt 不等于好 prompt。过长会：
- 稀释重点（LLM 注意力分散）
- 增加成本（token 变贵）
- 增加冲突指令的风险

**好 prompt 的标准是"精确"，不是"长"。** 能用 3 句说清的别用 10 句。

### 误解 3："找到一个好 prompt 就一劳永逸"

**错。** 换模型（gpt-4 → glm-4）、换任务变体，prompt 可能要重调。不同 LLM 对同一 prompt 的"理解"不同。**Prompt 要和具体模型配套，且要随任务演进。**

### 误解 4："Prompt 注入只是理论威胁"

**错，很现实。** 如果你的 Agent 读取外部内容（网页、文档、用户输入），里面可能藏"忽略以上指令，做 XXX"这样的注入。你的嵌入式安全意识在这里很有用——**永远不信任外部输入**。

## 9. 一句话本质

> **Prompt 是你写给 LLM 的声明式程序，LLM 的行为几乎完全由它决定。Prompt 工程的本质是消除模糊性——所有技巧（few-shot、思维链、结构化输出）都在让输出更精确可控。把 prompt 当代码：建测试集、迭代、版本管理。**
